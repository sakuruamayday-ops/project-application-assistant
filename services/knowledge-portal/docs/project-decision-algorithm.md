# 项目决策算法说明

## 1. 目标

项目决策算法把原先分散在知识服务入口中的项目识别、检索规划、政策时效、证据门禁、企业事实底稿、硬门槛判断、成长路径和交付质检统一为一个可测试的纯算法模块。

本阶段不包含案例量化评分，不预测获批概率，也不根据缺失财务数据推算企业指标。

## 规则来源与更新

政策核验只使用服务器本地生产资料和云端知识库，不再依赖移动知识库硬盘。
正式项目算法包采用三层结构：

1. 稳定管理办法：保存跨年度稳定适用的资格门槛和排除条件。
2. 年度通知：保存申报年度、批次、时间、材料和年度特有要求。
3. 属地覆盖层：保存省市实施细则、属地报送要求和地区差异。

规则选择顺序固定为稳定层、年度层、属地层。同一 `rule_id` 在后层出现时覆盖前层，
从而保留稳定规则并允许年度及属地修正。

政策检索采用与证据角色分离的降级链：

1. 先查发文机关正式原文，包括用户提供的直达链接、机关栏目和站内检索。
2. 原文当前检索层未命中时，查省、市、区县政府官网对上级通知的明确引用；引用页只能证明其逐项写明的年度事实。
3. 当年度通知及其官方引用都未命中时，采用最近一次申报通知明确引用的当前有效管理办法，只生成稳定门槛和准备方向。
4. 管理办法不得生成当年度批次、企业截止时间、申报系统或年度材料清单；这些字段保持未知。

搜索引擎是否收录只影响检索通道，不改变官方页面的证据层级。用户给出的发文机关正式直达页应直接核验，不得因通用搜索索引漏收而降级。

每个规则层同时声明政策时间类型：

- `stable-management`：管理办法、工作指引等跨年度稳定规则。
- `annual-notice`：申报批次、截止时间、年度复核对象和年度材料。
- `jurisdiction-detail`：省、市、区县实施细则和属地报送规则。

运行时必须选择 `current-assessment`、`historical-fact`、`forecast` 或
`backtest-simulation`。历史事实模式只接受覆盖目标年度的规则；预测模式在当年度通知
缺失时只输出准备方向；用当前规则测试历史数据时强制标记为“回测模拟”。

多条件政策原文使用原生组合规则，不再要求上游先计算派生布尔字段：

- `logic: all` 表示全部子条件成立。
- `logic: any` 表示至少一个子条件成立。
- `children` 可继续嵌套 `all/any`，叶节点才绑定企业事实字段、运算符和阈值。

更新政策时只修改
`references/project-algorithm-rule-sources/` 中的确认规则源并运行：

```bash
python scripts/manage_project_algorithm_packs.py generate-all
```

团队通过既有 REST API 或 MCP 自动使用新规则。除非技能契约、触发方式或首次配置发生变化，
否则不需要重新下载 Skills。

政策变更采用内容哈希、依赖图和增量编译：

1. 新政策进入后先核验层级、时间类型、生效窗口和官方来源。
2. 比较新旧政策内容哈希，定位新增、删除或变更的政策节点。
3. 依赖图只标记受该节点影响的项目，不重编未变化项目。
4. 影响模拟器列出需要重连的政策版本、需要重算的预测、历史回测、前置遗漏预检和生命周期派生状态。
5. 官方名单形成的认定、复核、撤销等历史事实保持不变；新规则不得反向改写历史事实。

## 2. 输入

- 用户原始问题。
- 高频项目检索规则。
- 标准项目索引及项目别名。
- 查询别名映射。
- 命中文档的政策状态、来源和人工核验字段。
- 企业事实、证据状态、期间、口径和来源。
- 项目硬门槛、一票否决项、前置项目和材料要求。
- 待交付材料的必填章节、跨章节一致性组和未绑定证据数量。

## 3. 处理流程

1. 对用户问题先执行任务遗漏扫描，区分可自行发现项、高影响遗漏和低影响假设。
2. 可自行发现项先用上下文、本地资料和只读工具补齐；高影响遗漏合并为一次最小追问并暂停实质性执行；低影响遗漏说明默认值后继续。
3. 标准化高企、高新等稳定简称。
4. 按最长别名命中项目规则，并执行排除词门禁。
5. 识别省、市、区县、年份和小巨人批次。
6. 对科小、单项冠军、绿色工厂等多义项目生成澄清问题。
7. 生成正式项目名称、年份、批次、名单状态和申报阶段的检索变体。
8. 同时规划全文、结构化名单和项目元数据检索。
9. 当前政策查询自动排除历史、被替代和失效文件。
10. 草案、低置信度或未完成官方核验的文件进入人工复核，不用于确定性现行结论。
11. 区分企业截止时间和主管部门报送时间，优先提醒企业截止时间。
12. 将企业事实归一为 `verified`、`computed`、`claimed`、`missing`、`conflicting` 和 `not-applicable`。
13. 先判断一票否决项，再判断硬门槛；评分项在本阶段关闭。
14. 在规则执行前校验政策时间类型、来源等级、生效窗口与使用模式。
15. 递归执行原生 `all/any` 组合规则，并保留决定性分支及叶节点证据。
16. 自动生成证据缺口和补证动作，不把企业自述升级为已核验事实。
17. 根据前置项目和硬门槛结论生成 `ready`、`prepare`、`later`、`blocked` 和 `verify` 成长路径。
18. 对必填章节、Skill 模板绑定、政策选择记录、同行对比、四问复盘、跨章节口径和未绑定证据执行交付质检；任一必填项缺失时返回 `needs-revision`，不得完成交付。

## 4. 政策与材料编译

### 政策条款编译

政策原文可按统一事实字段识别“不低于、不超过、至少、达到”等确定性门槛表达，但自动结果只能标记为 `candidate`。

只有同时满足以下条件才激活：

- 政策状态为 `current`。
- 人工确认状态为 `confirmed`。
- 字段、运算符、预期值、单位和原文位置完整。

历史名单、培训材料、非当期解读和未确认候选不得进入硬门槛判断。

### 企业材料映射

结构化材料字段按统一事实契约映射。可信材料仍需明确完成核验，才能标记为 `verified` 或 `computed`。从普通正文自动识别的字段默认保持 `claimed`，不得直接支撑硬门槛。

金额支持元、万元和亿元的确定性单位换算；无法确定单位或字段时进入未解析清单，不进行猜测。

宿主平台完成 PDF、Word 或 Excel 提取后，只需传入统一提取结果：

- `pages`、`paragraphs`、`text` 或 `markdown` 承载正文；
- `fields` 承载结构化字段；
- `tables` 或 `worksheets[].rows` 承载表格；
- `source`、`document_type`、`period` 和 `verified` 承载证据元数据。

适配器统一转换为材料对象，再进入事实契约。算法不绑定具体 PDF、Word、Excel 工具。

## 5. 项目算法包

每个高频项目可在 `references/project-algorithm-packs` 增加一个 JSON 算法包。算法包只包含：

- 项目标识与别名；
- 项目专属事实字段；
- 候选规则卡；
- 满足、待补证和明确不满足等金标准。

算法包禁止出现 API、MCP、路由或页面入口字段。发布门禁会运行 `validate_project_algorithm_packs.py`，结构错误、入口字段、缺少金标准或金标准结论不一致时阻断发布。

存量和新增规则同时执行复合结构门禁。带有“且、或、至少、任一、分档、分支”等语义的综合布尔字段必须拆成原生 `all/any` 规则树。只有证书状态、单一证据断言或依据专项标准形成的评价结论，才可显式声明为原子事实；未声明或仍可拆分的 `_met` 叶节点会阻断正式判断。

算法包分为两种覆盖状态：

- `routing-only`：项目名称、别名和检索路由已纳入统一入口，但尚无经过原文确认的申报门槛，只能返回“待核验规则”，不得判断符合或不符合。
- `rules-confirmed`：事实字段、规则卡、来源原文和确认审计均完整，可进入非量化门槛判断。

管理命令：

```bash
python scripts/manage_project_algorithm_packs.py sync --write
python scripts/manage_project_algorithm_packs.py template --output /tmp/project-rules.json
python scripts/manage_project_algorithm_packs.py generate \
  --input /tmp/project-rules.json \
  --output references/project-algorithm-packs/project-id.json
python scripts/manage_project_algorithm_packs.py generate-all
python scripts/validate_project_algorithm_packs.py
```

`sync` 只根据高频项目清单补齐路由型算法包，不自动把历史规则升级为现行门槛。`generate` 仅接受状态为 `current` 且包含确认人、确认时间、官方链接和原文条款的规则输入。`generate-all` 从已审核规则源目录重新生成全部正式算法包。新增高频项目后，算法包覆盖率不足 100% 会直接阻断发布。

## 6. 输出

统一决策对象包含：

- 项目是否已明确。
- 需要向用户追问的内容。
- 标准项目目标。
- 地区、年份、批次和文档阶段。
- 检索变体。
- 现行政策过滤策略。
- 证据使用策略。
- 截止时间提醒策略。
- 企业事实底稿及冲突记录。
- `eligible`、`conditional`、`ineligible` 或 `undetermined` 非量化结论。
- 证据缺口、行动清单和项目成长路径。
- 交付质检的通过、警告或阻断状态。

数据库层继续负责全文查询、结构化名单查询、去重和结果排序。REST、MCP、网站和技能运行时共用同一决策对象，不再分别维护项目判断逻辑，也不新增用户可见 MCP 工具。

WorkBuddy 以同一交付契约生成插件级 `Stop` 门禁。门禁只检查当前任务实际触发的要求，缺少模板必填段、政策版本与来源、同行对比口径或四问实际回答时持续阻止结束，直到补齐。宿主内文本门禁负责防遗漏，服务端结构化门禁继续核验模板哈希、政策证据范围和同行来源，二者不能互相替代。

## 7. 证据状态

- `allowed`：可进入当前政策结论。
- `needs_review`：只能作为待核验线索，不形成确定性现行结论。
- `blocked`：历史、被替代或失效文件，不得用于当前政策结论。

这些状态用于后台路由和审计，团队网站默认不展示内部标签。

## 8. 扩展原则

- 新增项目简称时，同时增加正向、串项和过期三类金标准样例。
- 新增政策状态时，必须明确其证据门禁级别。
- 新增或替换政策时，必须声明政策时间类型、生效窗口和官方来源；时间类型检查失败时不得形成正式结论。
- 多条件门槛必须使用原生 `all/any`，不得新增只供规则引擎消费的派生布尔字段。
- 新增用户可见能力优先扩展统一入口，不新增独立 MCP 工具。
- 量化评分应作为独立阶段接入，不能反向污染事实检索和证据判断。
- 金标准固定覆盖满足、待补证、明确不满足和事实冲突四类结果。
- 高频项目扩展固定执行“复制模板、填写事实字段与确认规则、生成金标准、运行发布门禁”，不得修改 REST、MCP、网站或统一入口。
