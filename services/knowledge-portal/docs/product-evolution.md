# 企业全生命周期助手网站与 Skills 迭代约定

## 版本基线

- 网站与 GitHub 当前正式版本统一为 `V1.3`；`V1.0`至`V1.2`作为历史版本保留。
- 原 `2.1.x`、`2.2.0` 仅保留为内部演进记录，不再作为对外版本编号。
- 后续版本不自动发布，必须先由主人和焦糖共同确认更新日志。

## 更新日志协作流程

1. 汇总本轮真实变更、测试结果、配置变化和兼容性影响。
2. 焦糖形成更新日志初稿，按新增、优化、修复、配置变化、升级方法和已知问题分类。
3. 主人删改并确认最终表述。
4. 通过依赖审计、安装验收和发布包门禁。
5. 先创建 GitHub 预发布，并再次核对发布包、版本、签名和 SHA-256。
6. 不维护 macOS 或 Windows 平台确认状态；具体兼容问题按用户环境单独处理。
7. 网站登记成功后，GitHub 预发布才提升为正式 Latest。

## 网站整改路线

1. 信息架构：把成员工作台与管理员后台拆成两个清晰层级，首页只保留高频任务。
2. 产品组件：统一表单、弹窗、标签页、表格、分页、空状态、危险操作确认和反馈状态。
3. 视觉系统：保留焦糖红，减少大面积渐变、重复卡片和装饰性英文，建立字体、间距、圆角和状态色规范。
4. 内容表达：按钮使用动作结果命名；专业字段提供就地说明；危险操作明确影响范围与回滚方式。
5. 响应式：重点验证登录、知识答疑、Token生成、知识库管理和政策校准在手机与窄屏下的可用性。
6. 无障碍：完善键盘焦点、表单错误、对比度、语义标题、表格移动端替代呈现和减少动效。
7. 发布验收：每次上线执行桌面、手机真实浏览器冒烟测试，并检查控制台错误、核心按钮和权限边界。

## 技能使用顺序

- 从零页面：先用 Build Web Apps 或现有后端模板跑通功能骨架。
- 现有页面：用 Impeccable 的 critique、audit、layout、typeset、harden 和 polish 思路二次打磨。
- 视觉气质：用 Taste Skill 确定布局变化、动效强度和信息密度，避免模板化页面。
- 记忆点：用 Frontend Design 将视觉强化集中在一个能代表政策知识服务的标志性元素上。
- 产品界面：借鉴 shadcn 的组件状态、可访问性和组合方式，但当前 Jinja 页面不直接引入 React 依赖。
- 展示页面：只有版本介绍、使用手册或分享页才采用 Beautiful HTML Templates，不套用到管理后台。
- 发布验收：最后使用真实浏览器和 Playwright 检查桌面、移动端与交互状态。
