# 项目前期评估与可行性分析双报告合同

## 适用范围与冻结边界

本合同只统一“项目前期评估报告”和“项目申报可行性分析报告”的交付结构、证据状态、补强表达、截止日期和品牌要求，不替代项目领域规则。企业分析报告 A、B、C 版，尖兵领雁、市级重大及科技计划类的既有分析逻辑保持不变；如需输出本合同的报告形式，只改变呈现和补强清单，不改变其原有资格、技术、预算、评分和验收判断。

项目核心判断继续由领域技能负责：高企使用四关联，三首使用产品分类与成熟度证据，研发中心使用当期评分表，专精线使用现行梯度培育规则，绿色、数字化、质量品牌及科技计划使用各自既定口径。不得用统一模板覆盖领域差异。

## 项目与版本确认

1. 先确认企业主体、地区、申报年度、项目全称、申报层级、批次以及新申报或复核。
2. 普通项目的省级、市级或区县级选择会改变条件、评分或截止时间，而用户输入仍然模糊时，提出一次最小必要确认并暂停依赖该选择的结论。
3. 首台套、首批次新材料和首版次软件不得要求用户先选择国际、国内、省内或市级档次。先核验所在地、申报产品、目录、技术创新、成熟度、检测查新、首用销售和知识产权，再给出首选层级与备选层级；证据不足时给出降级申报路径。
4. 每个项目先取得现行管理办法、工作指引和当年度通知。目标年度通知未发布时只写“规划参考，待当年通知”，不得复制历史截止日期、奖励金额或年度特有门槛。

## 当年度截止日期

当年度项目必须在项目路径表和项目详表中增加“申报截止日期”字段，并以报告基准日判断窗口状态：

- 仍在申报期：写完整日期和批次，例如“2026年9月10日截止”；
- 已截止：写“2026年7月17日已截止”，并把行动改为受理跟踪、反馈补正、转下一批、复评通过或下一年度重启；
- 分批申报：分别列地方网、国家网或第一批、第二批截止日期，不合并为一个日期；
- 常年或滚动受理：写明“常年受理”或具体批次规则；
- 未来通知未发布：写“待当年通知”，不得给确定日期。

已经截止或临近截止的重新认定、复核和在审项目，报告重点必须是确保本轮通过、补正和状态闭环，不能继续安排泛化的长期准备。

## 证据状态与补强表达

每个通知条件逐条映射以下状态，并给出补强动作：

- `已具备`：企业材料或已核验来源足以支撑；
- `企业提供待核`：企业陈述或材料尚未完成交叉核验；
- `待企业确认`：资料未提供，当前无法判断；
- `当前检索层未命中`：公开或内部检索未发现，不能据此断言不存在；按申报证据尚未闭合处理；
- `明确未具备`：企业资料或企业确认能够证明尚未完成；
- `存在差距`：已有可比数据低于通知条件；
- `冲突待核`：两个来源、期间或口径不一致；
- `不适用`：通知条件经核验不适用于本项目或企业。

例如通知要求研发机构，而当前检索层未命中时，应写“当前检索层未命中研发机构，申报证据尚未闭合；待企业确认。如确未设立，建议完成组织文件、固定人员、设备场地、制度、项目和成果台账”，不得直接写成“企业没有研发机构”。高企的检测报告、产学研、成果转化、人员和知识产权等缺项使用同一规则。

## 通用科技咨询补强包

所有项目的两类报告均增加两份建议交付物：

1. 国内产品技术水平评价咨询报告；
2. 国际产品技术水平评价咨询报告。

两份报告分别围绕拟申报产品或核心技术开展同类产品检索、结构与功能比较、性能指标对标、关键技术先进性、国产替代和产业链价值分析。建议目标可以写为“经检索、对标和评价后，争取形成国内领先、国际先进的技术水平结论”，不得在证据形成前承诺已经达到该水平。

除非当期通知明确要求，两份科技咨询报告属于通用软提升和证据补强，不得冒充硬门槛或固定加分。报告必须说明它们对当前项目的具体作用，不能只在末尾机械列名。

## 报告一：项目前期评估报告

定位是首次接洽和谈单，默认简洁清爽。固定包含：

1. 总结结论：项目版本、窗口状态、总体判断、核心优势、关键差距和立即动作；
2. 申报条件对照：现行核心门槛、企业数据、证据状态和补强建议；
3. 项目专属核心对象：按项目路由切换，不机械使用主导产品或专利章节；
4. 实施路径：当年度截止日期、补数补证、补强项目和下一次判断节点；
5. 科技咨询补强：国内、国际两份报告的对象、目标和项目作用。

评分制项目在前期报告中只列决定可行性的核心门槛和关键得分项，不铺开完整评分表。没有数据的关键条件写“待企业确认”；与项目无关的合规套话不展开。

## 报告二：项目申报可行性分析报告

定位是合作后的实施决策。固定包含：

1. 项目版本、现行通知、申报层级、批次、截止日期和当前状态；
2. 三档结论：可申报、有条件申报、不可申报或暂无法判断，并说明依据；
3. 现行条件或完整评分表逐项拆解；
4. 企业值、证据来源、证据状态、确定得分、条件得分和差距；
5. 项目专属核心对象及跨证据链一致性；
6. 每项补强动作、材料、验收标准和完成节点；
7. 当年申报、补正、审核、复核或下一年度倒排计划；
8. 国内、国际科技咨询报告的实施内容和成果使用方式。

评分细则已经公布的项目必须拆完整评分表；未公布评分细则时只分析条件和竞争力，不虚构分值。缺少企业数据时不估分。政策合格线与内部安全目标必须分别列示。

## 专项补强接口

- 专精线额外核验“数字化转型诊断报告”：整体档次，发展战略、业务创新转型、新型能力、系统性解决方案、治理体系，全国和同行对标、优势弱项及提升路径。未提供时写“待企业确认，建议补强”，不预写档次、指数或排名。
- 高企额外关联“研发费用加计扣除规范化服务”：立项可研、项目清单、人员设备清单、工时记录、材料领用、小试中试、项目变更、结题成果、专利关联、月度费用分配、研发辅助账和研发明细账，并与高企研发项目、专项审计和纳税申报口径一致。

## 水印与双格式

两类报告及培训模板同时输出可编辑 Word 和 PDF，调用套件共享品牌运行时，使用共创红色居中水印及“共创研究院”页眉。不得另建水印资产或自行调整颜色、尺寸和透明度。

标准 Word 和 PDF 权限不能可靠实现“只加密水印、正文继续完全可编辑”。因此不设置文档加密或编辑限制：Word保持正文可编辑，PDF使用页面化水印。不得为了防删水印而限制用户编辑正文。

## 候选包十二类真实客户回归

常规项目模板进入候选发包前，使用根目录 `scripts/run_workbuddy_report_candidate_pipeline.py` 执行一条闭环流水线：

1. 私有夹具恰好覆盖高企、专精特新中小企业、小巨人、首台套、首批次、首版次、研发中心、制造精品、单项冠军、绿色工厂、数字化和科技计划十二类；同一企业可用于不同项目，但必须切换项目核心评估对象。
2. 每类至少绑定一份真实客户原件、文件 SHA-256 和可在原文命中的锚点；锚点未命中时不得成稿。客户原件、路径、企业名称和客户成稿不进入公共技能树或候选 ZIP。
3. 源码模板生成二十四份完整 Word 和对应 PDF，每页渲染为 PNG；结构、红色水印、占位符、证据状态和资料来源台账任一未通过时停止。
4. 只构建 macOS WorkBuddy 和 Windows WorkBuddy 两个未签名候选 ZIP，对每个最终 ZIP 安全解压，运行包内选模器，对十二类两类报告分别再成稿二十四次，共四十八次。最终 ZIP 的模板哈希、路由和成稿结构必须与源码候选一致。
5. 逐页自动渲染只证明可视化和页数完整。抽取前期评估首页与可行性分析条件页形成联系表，由人工或视觉模型检查缺字、裁切、重叠、表格可读性、层级和水印。抽检未完成时自动流水线回执必须保持 `pending-visual-review`；检查完成后使用 `scripts/record_workbuddy_report_visual_review.py` 绑定联系表哈希和二十四项检查结果，才能进入真实宿主测试。
6. 源码、模型和 ZIP 回归不代替 WorkBuddy 真实宿主回执。macOS 或 Windows 尚未在真实宿主安装、触发和交付时，分别写 `pending-real-host-receipt`，不得写成已验证兼容。
7. ZCode 不在本流水线范围内：不生成候选包，不写入发布清单，不给出通过状态，仅在未来独立宿主测试后再评估是否开发。
