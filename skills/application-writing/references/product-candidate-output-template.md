# 主导产品候选逐段输出模板

用于仅生成主导产品候选和六问结论的任务。它不是完整申请书、资格评估或政策评分模板。用户有更具体字段要求时沿用其字段；否则按下面的结构生成，不额外创建确认状态。

## 固定结构

```json
{
  "result": {
    "products": [
      {
        "name": "技术载体与产品特征组成的候选名称",
        "family": "该候选所属的商业产品类别",
        "linkedIpIds": [],
        "technologyCardIds": [],
        "relation": "该候选已知的材料、终端制品及专利支持关系；未确认关系在本句中明示",
        "directionQuestion": "针对这个候选需要用户作出的具体选择"
      }
    ],
    "sixAnswers": {
      "Q1": "产品载体：说明输入已给出的材料、产品或服务对象。",
      "Q2": "行业问题：说明这些资料实际指出的问题。",
      "Q3": "技术方法：说明已给出的结构、工艺或方法，分别标明来源。",
      "Q4": "性能与产业化：逐项保留已给指标的数值、单位、测试对象和方法；未提供的部分明确列为缺项。",
      "Q5": "产业链价值：说明现有方法的用途；拟组合路线按条件建议表述。",
      "Q6": "名称归纳：给出候选名称、归纳理由及具体方向确认问题。"
    },
    "supportingIpIds": []
  },
  "basis": [],
  "missing": [],
  "nextAction": []
}
```

数组中的引用只取输入实际存在的ID。`linkedIpIds`与`technologyCardIds`分别保存专利和技术卡，不交叉填入。`basis`记录实际依据，`missing`只保存一份缺项清单。

## 每部分怎么仿写

1. **名称**：采用“技术载体或方法特征＋可识别的产品类别”。范文只提供句式，不提供当前企业的材料名称、指标或专利。
2. **关系**：优先写“技术卡描述的〔材料〕经〔方法〕形成〔终端产品〕”。若另一项专利涉及该类产品的结构，但输入未给出对应关系，接着写“〔专利ID〕描述〔结构〕，尚未确认用于上述产品”，不能用“其结构为”连接两项资料。
3. **组合建议**：允许提出有意义的组合方向，但直接写“若用户确认〔技术卡〕与〔专利〕属于同一产品，可将〔组合名称〕作为候选”。六问中涉及同一组合时保持这个条件，不把建议写成已实施事实。
4. **方向问题**：写具体问题，例如“该候选应以功能基材还是终端制品作为主导产品载体？”不能用“是否确认以上内容”替代业务选择，也不能代答“已确认”。
5. **设备支撑**：仅有设备专利、没有该设备对外产品或服务依据时，将ID放在`supportingIpIds`，不放进`products`，不计入产品数量。
6. **指标**：采用“〔测试对象〕的〔指标〕为〔数值＋单位〕，方法为〔已提供方法〕”。没有指标则写“主要技术指标待补充”，不使用范文数值补齐。

## 段落仿写示例

以下为表达骨架，方括号是输入字段说明，不得直接输出，也不得借此补造事实：

> 技术卡〔ID〕记载，〔材料或载体〕通过〔已给出的方法〕形成〔产品〕，用于解决〔资料明确指出的问题〕。其〔测试对象〕的〔指标〕为〔数值与单位〕，测试方法为〔方法〕。据此建议将〔候选名称〕作为主导产品方向，需明确采用〔载体A〕还是〔载体B〕作为申报对象。

缺少指标时省略整句指标叙述，将具体缺项写入`missing`，不输出空括号或从示例补值。只有一个合理载体时询问该方向是否符合实际业务，不强行制造第二选项。另有未关联专利时单独写：

> 〔专利ID〕涉及〔已知结构〕，现有输入尚未确认其用于上述产品。若确属同一产品，可进一步考虑〔组合候选〕；在确认前仅作为备选方向，不作为既有技术关系。

## 确认与修改方式

此模板只生成候选，不包含`directionConfirmed`。已有用户确认由调用方作为上游输入传入并保留，模型不得自行新建确认记录。修改某一问时只重写该问及确实受影响的下游部分，保留其他已确认内容。

## 验证边界

模板示例不是本轮事实，也不是模型实跑回执。使用新会话、相同输入验证事实和结构；允许措辞不同，不要求逐字复刻范文。遇到缺项先交付成立部分和具体问题，不反复补造数据或整段重跑。
