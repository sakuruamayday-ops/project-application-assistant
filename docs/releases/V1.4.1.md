# 企业全生命周期助手 V1.4.1

发布日期：待主人确认后填写

V1.4.1 是 WorkBuddy 跨版本升级与发布事务增强版。版本保持 49 项顶层 Skills 和 V1.4.0 业务规则，不重新登记已经通过门户验收的设备；通用签名包和 WorkBuddy 跨平台签名包均重新构建，不覆盖 V1.4.0。

## 套件清单版本事实

V1.4.1 增加已绑定 WorkBuddy 设备的跨版本升级事务，在不重新登记设备、不轮换密钥和访问凭据的前提下完成签名包升级、连接复核与失败回滚。

- Skills 中心会比较已验收设备版本与最新 WorkBuddy 正式包，只在存在更高版本时显示跨版本升级按钮。
- 升级采用审查与明确授权两步流程，固定源版本、源包哈希、目标版本、目标包哈希和原设备绑定，计划生成后不跟随后续发布漂移。
- 升级复用现有设备标识、Ed25519 设备密钥、API Token、bootstrap_url 和 jiaotang-kb MCP 身份，不创建第二套登记或连接。
- 目标包必须通过 SHA-256、Ed25519 签名和发布者指纹核验；只有目标版本、目标包哈希和 jiaotang-kb 只读连接复核全部一致，门户才更新设备版本。
- 升级失败时恢复升级前插件目录并保留原设备身份和系统凭据；失败阶段会回传门户，频控、临时网络错误或验签失败不得冒充升级成功。
- 设备绑定新增已安装版本、包哈希、安装时间和最近升级时间，历史安装结果与升级结果使用同一可审计状态面板。
- 发布端使用带 Ed25519 签名哈希清单的全局单写租约，GitHub、知识门户和安装端必须属于同一发布事务；其他任务只能只读监控。
- 49 项顶层 Skills 与 V1.4.0 业务规则保持不变；V1.4.0 已绑定设备升级 V1.4.1 时无需重新登记。

## 跨版本升级流程

门户读取当前设备已经回传并验收的安装版本及包哈希，再与最新 WorkBuddy 正式包比较。只有源版本低于目标版本时才开放升级入口。

第一步生成只读审查计划，固定源版本、源包哈希、目标版本、目标包哈希、设备绑定和设备公钥。第二步由用户明确授权同一个 Agent 继续升级。Agent 只能下载计划固定的目标包，并必须核对 SHA-256、Ed25519 签名和发布者指纹。

升级不会创建新的设备绑定、设备公钥、API Token、bootstrap_url 或 jiaotang-kb MCP。新包启用后必须完成一次只读知识库调用；回传的版本和包哈希与目标不一致时，门户拒绝把设备标记为升级成功。

## 回滚

- 升级前保留当前插件目录作为可恢复备份。
- 目标包验签、插件启用或 jiaotang-kb 连接复核任一步失败时，恢复升级前插件目录和原版本包。
- 回滚不得删除持久 jiaotang 市场、设备绑定、设备密钥、API Token、bootstrap_url、个人偏好或本地项目资料。
- 升级失败会记录失败阶段和下一步，不把网络错误、频控、哈希不一致或签名失败记为成功。

## 发布事务

全局发布锁已经作为服务端热更新部署。V1.4.1 的 GitHub 候选版本、知识门户候选版本和安装端提升使用同一个带签名哈希清单的发布事务；同一版本同时只允许一个任务持有发布租约，其余任务只读监控。

正式提升仍遵守两阶段确认：先创建预发布并在门户登记候选包，待主人确认网站介绍、用户手册和候选包哈希后，才执行安装端原子提升、门户正式发布和 GitHub Latest 切换。

## 安装与兼容性

- 新设备通过门户两步流程安装 V1.4.1 WorkBuddy 包。
- 已绑定 V1.4.0 设备使用 Skills 中心的两步升级入口，不重新登记。
- WorkBuddy macOS 与 Windows 使用同一个跨平台签名包。
- macOS 继续复用系统钥匙串中的设备凭据。
- Windows 包结构、签名和升级协议门禁会自动执行；真实 Windows 升级与重启保留“待主人实机验收”标识。

## 已知限制

- V1.4.0 发布前已经绑定但没有回传已安装版本和包哈希的设备，门户不会猜测源版本；需由管理员核验原安装记录，确认版本与包哈希后才开放升级。
- WorkBuddy 应用内真实升级仍需由正在运行的 WorkBuddy 执行；外部脚本不会启动宿主、绕过权限或冒充应用内验收。
- 网站介绍和最终 Word 用户手册须经主人确认后才能正式提升。
