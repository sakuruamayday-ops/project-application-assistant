# 外部产品与研发技能评估

核验日期：2026年7月26日

核验方式：GitHub API、仓库 README、SKILL.md 与关键模板。Star 数为核验时快照，会继续变化。

## 1. 结论

本轮不把这些仓库整包安装进企业全生命周期助手，也不复制其技能正文。采用方式是：

- 用 pm-workbench 收敛产品判断和轻量产品文档结构。
- 在 PRD 确认后，用 Spec Kit 管理规格、技术方案、任务和实现顺序。
- UI UX Pro Max 留到已有工作流验证后，用于具体页面设计，不用于决定产品范围。
- 代码评审、重构、测试、CI 和 README 类 Skills 作为维护流程参考；当前产品已有测试、发布门禁和文档体系，后续只补真实缺口，不增加重复 Skill。

## 3. pm-workbench

### 值得采用

- 先解决最上游的产品问题，再写文档或进入实现。
- 默认只补最少的关键信息，信息不足时可以输出带假设的 v0，而不是无限追问。
- PRD Lite 保留问题、用户、目标、方案、范围、风险和下一步。
- Roadmap 必须写出阶段目标、保护的稀缺资源、明确不做项和改变路线的条件。

### 不直接安装的原因

- 它是通用 PM Skill，当前任务只需要其方法，不需要长期占用触发空间。
- 本产品已经有明确的业务规则和发布治理，整包安装会增加一套平行模板体系。
- 当前应先验证产品文档是否推动 V1.2 决策，再决定是否沉淀为本项目自己的产品管理 Skill。

### 本轮已吸收

`product-brief.md`、`prd-v1.2.md` 和 `roadmap.md` 已采用其上游问题优先、PRD Lite、明确不做项和条件式决策方法，但内容全部基于当前仓库事实重写。

## 4. Spec Kit

### 值得采用

- `specify` 将需求转成可测试规格。
- `plan` 读取规格和项目约束后形成技术方案。
- `tasks` 按依赖顺序生成带文件路径的任务。
- `implement` 按任务推进并在失败时停止。

### 使用时点

Spec Kit 解决的是“方向确定后如何规范施工”，不负责决定产品应该做什么。当前先完成产品基线与 V1.2 PRD；主人确认后再为 V1.2 建立 feature 目录。

### 适配方式

- 保留仓库现有 AGENTS、测试和发布门禁，不让 Spec Kit 覆盖本项目规则。
- 先写一个 V1.2 feature，不在全仓一次铺开。
- 将真实性、隐私、跨宿主和非破坏性文件规则写入规格约束。

## 5. UI UX Pro Max

仓库当前 README 已更新为 84 种 UI 风格、192 套调色板、74 组字体搭配、22 个技术栈和 161 条行业规则，用户提供的 67、161、57 是旧版本宣传口径。

它适合在以下条件成立后使用：

- 已明确一个具体页面和核心用户任务。
- 信息架构、字段和状态已经稳定。
- 能用真实浏览器验证响应式、键盘操作、对比度和错误状态。

当前不应先让 84 种风格参与决策。企业全生命周期助手需要的是可信、克制、数据密集且可审计的专业工作界面，视觉选择应服从任务闭环。

## 6. 代码评审与重构类 Skills

### code-review-expert

优点是覆盖变更范围、SOLID、安全、错误处理、性能、边界条件和并发风险，并用 P0 至 P3 表达严重程度。适合作为 PR 合并前的评审清单。

不足是默认面向当前 Git diff，不能替代本产品已有的业务规则测试、政策新鲜度、证据链和发布包验签。

采用建议：后续把其高价值检查项映射到现有发布门禁，不新增对用户可见的业务 Skill。

### refactor-advisor

优点是能快速发现长函数、大类、重复代码和耦合。当前门户主应用文件较大，这类扫描有现实价值。

不足是“函数超过 50 行”“类超过 300 行”等阈值只能作为线索，不能机械触发重构。V1.2 应先以用户闭环为目标，重构只服务于交付风险和变更频率。

采用建议：在 V1.2 技术方案阶段针对高变更路径做定向重构评估，不启动全仓清洁行动。

## 7. 测试、CI 与 README 类 Skills

### test-generator

其“先读真实契约、区分当前行为与产品期望、实际运行测试、不自动安装框架”与本项目要求一致。V1.2 可用其方法补充三条端到端金标准任务，但不能只生成单元测试。

### github-actions-gen

其最小权限、PR 不接触 Secrets、Action 固定完整 SHA、设置超时和实际验证等规则值得采用。当前仓库已有发布脚本和门禁；是否补 GitHub Actions 应由真实托管与发布流程决定，不为了“有 CI”而新增空流水线。

### zh-readme

其“先读代码、首屏解释是什么、适合谁、如何开始”适合维护根 README。V1.2 已据此重写首屏，并补充下载、兼容状态、安全边界、文档导航和受控发布流程。

## 8. 是否需要寻找其他技能

当前不需要继续广泛搜索。现阶段的上游缺口是产品决策与版本契约，不是工具不足。只有在 V1.2 规格确认后出现以下明确缺口时再搜索：

- 现有工具无法生成跨宿主可验证的规格与任务。
- 无法对端到端 Agent 工作流做稳定评测。
- 无法在不上传客户材料的前提下记录产品事件。
- 现有设计工具无法处理数据密集型专业后台的无障碍与状态设计。

搜索应围绕具体缺口进行，不以 Star 排行榜扩充工具箱。
