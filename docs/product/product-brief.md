# 企业全生命周期助手产品基线与定位

状态：产品基线 V1.4.8

更新日期：2026年8月2日

## 1. 一句话定位

企业全生命周期助手是面向政府项目申报工程师和知识产权顾问的专业 Agent 工作系统，把分散的政策、企业、财务、知识产权与申报材料转化为可追溯的判断和可复核的交付物。

它不是通用聊天机器人，也不是单纯的政策搜索网站。核心价值是把专业工作方法、团队知识和质量门禁组织成可重复执行的业务闭环。

## 2. 当前阶段结论

产品已完成“能力供给”阶段，正在进入“工作流产品化”阶段。

截至 2026年8月1日，正式内容基线为 49 个 Skills。后续分发只保留通用 Skills 与跨平台 WorkBuddy 插件市场包两个目标，macOS 与 Windows 共用同一个 WorkBuddy ZIP。产品同时具备团队知识库、成员门户、智能问答、REST API、远程 MCP、Skills 分发、偏好同步、知识校准和发布治理。以上事实来自 `skills/suite-manifest.json`、发布说明、用户手册和知识库服务文档。

成员门户提供黑金风格 Skills 管理中心。所有登录成员均可浏览 49 个正式技能，查看说明、文件结构、协作关系与原始 `SKILL.md`，并下载官方套件。WorkBuddy 用户点击“一键安装”后，只需复制一段完整指令；Agent 自动安装或更新 49 项 Skills、启用最小行为 Hook、只替换 `mcpServers.jiaotang-kb`、保留其他 MCP，并在一次重载后调用 `knowledge_service_status` 验收。手工配置页自动复用或生成当前登录用户的个人 Token，并直接填入完整远程 MCP 配置。

Skills 发布门禁以正式清单、逐技能发布文件、签名材料和逐文件 SHA-256 为准，不把页面截图回归设为发布阻断条件。截图仅用于设计阶段人工目视检查。

当前阻力不再是“有没有能力”，而是：

- 用户面对 49 个 Skills 时仍可能不知道从哪里开始。
- Skills、知识库和门户已经可用，但一次客户任务的上下文、证据、判断、缺口和交付物还缺少统一项目档案。
- 产品标签、语义版本和组件版本已统一为 V1.4.8、1.4.8；旧版本仅允许出现在历史发布、迁移、审计或测试语境。
- 发布编排已显式区分代码与索引：纯代码发布通过固定 `code` 入口只验证签名回执和 current 指针，索引变化才执行全库扫描；索引发布持续回报分阶段墙钟、传输字节和完成百分比。
- 当前测试更擅长证明模块可运行，还缺少对端到端业务任务是否真正完成的统一验收。

因此，下一阶段不以增加 Skill 数量为成功标准，而以真实任务闭环、结果可追溯和用户重复使用为标准。

## 3. 目标用户

### 核心用户

政府项目申报工程师。

他们需要快速识别项目机会、核验企业条件、形成申报策略、撰写材料并控制跨章节一致性。最大成本不是“写一段文字”，而是反复查政策、找资料、对口径、复算数据和返工。

### 重要用户

知识产权顾问。

他们需要把专利检索、权利状态、技术路线、项目申报和客户产品价值连接起来，而不是分别输出互不关联的专利清单与申报建议。

### 支撑用户

团队管理员和产品维护者。

他们负责成员准入、知识更新、政策校准、Skills 发布、故障定位和质量治理，需要知道产品是否可用、哪些环节正在失效、更新是否真正改善业务结果。

### 暂不作为核心用户

- 不具备专业判断能力、只希望一键生成申报书的普通企业用户。
- 需要 CRM、合同、回款、工时和人员排期的综合经营管理团队。
- 期待系统自动登录、自动提交或代表用户联系政府与客户的用户。

## 4. 核心待办任务

用户真正要完成的不是“调用一个 Skill”，而是以下工作：

1. 我拿到一家企业后，先判断有哪些项目值得做，而不是把所有政策都看一遍。
2. 我确定目标项目后，快速知道硬门槛、得分空间、资料缺口和最晚动作时间。
3. 我开始写材料时，能够复用已经核验的企业事实、财务数据、知识产权和政策依据。
4. 我交付前，能够发现数字、产品口径、技术叙事、政策版本和知识产权之间的冲突。
5. 我下次继续同一客户时，能够恢复已确认决定，不再重复检索和追问。

## 5. 产品价值主张

### 对一线顾问

- 少找：先路由到正确项目、政策和证据层。
- 少猜：事实、计算、推断和待补资料分开呈现。
- 少返工：同一客户事实进入共享项目档案，后续环节复用。
- 可交付：输出直接服务于判断、材料、复核和下一步动作。

### 对团队

- 把优秀顾问的方法变成可执行流程，而不是散落在个人聊天记录里。
- 把知识更新、政策新鲜度和人工校准纳入治理。
- 通过业务闭环指标判断产品价值，而不是只看 Skill 数量和调用次数。

## 6. 核心业务闭环

```mermaid
flowchart LR
    A["模糊业务问题"] --> B["任务澄清与路由"]
    B --> C["项目档案"]
    C --> D["政策与企业证据"]
    D --> E["匹配或可行性判断"]
    E --> F["材料与行动方案"]
    F --> G["一致性与质量门禁"]
    G --> H["交付、归档与复盘"]
    H --> C
```

每个环节都必须能回答三个问题：用了什么依据、还有什么缺口、下一步由谁做什么。

## 7. 产品组成

| 产品层 | 当前职责 | 下一阶段重点 |
|---|---|---|
| Agent Skills | 专业判断、路由、写作、核验和受控进化 | 统一输入输出契约，减少用户理解 Skill 名称的成本 |
| 团队知识库 | 政策、名单、案例和内部方法检索 | 让每条关键结论可回到原文和核验状态 |
| 门户与 MCP | 成员准入、问答、连接、下载、偏好和管理 | 展示项目闭环状态，而不只是资源与系统状态 |
| 发布治理 | 验签、依赖、测试、版本和回滚 | 增加端到端业务任务金标准和文档一致性门禁 |

## 8. 产品原则

1. 先判断，后写作。没有完成政策与企业事实核验时，不生成伪完整正式结论。
2. 一个入口。用户用业务语言提出任务，不要求记住 Skill 名称。
3. 一份事实，多处复用。企业、期间、口径和来源一致时，不重复提取和追问。
4. 缺口可见。当前检索层未命中、资料不足和外部能力不可用必须明确显示。
5. 结果可追溯。数字、日期、政策、企业事实和知识产权结论能回到来源或计算过程。
6. 高风险动作需确认。不自动提交申报、不代表用户联系第三方、不静默上传客户材料。
7. 业务闭环优先于功能数量。新 Skill 必须证明现有闭环无法覆盖，才进入产品范围。

## 9. 北极星指标与护栏

### 建议北极星指标

每周完成的“可复核业务闭环”数量。

可复核业务闭环是指一次任务至少包含明确对象与目标、已引用证据、可执行判断、显式缺口、下一步和质量检查结果。单次搜索、单段文案和仅打开门户不计入。

### 支撑指标

- 首次有效判断时间：从提出任务到形成第一版可执行结论的时间。
- 闭环完成率：启动项目档案后完成判断与质量门禁的比例。
- 证据完整率：关键事实中具备来源、时间和口径的比例。
- 返工率：因政策版本、数据口径或跨章节冲突导致的重复修改比例。
- 复用率：同一项目档案在后续阶段被成功恢复和继续使用的比例。
- 周活跃顾问数与四周留存。

### 护栏指标

- 无来源高风险结论数量。
- 使用过期政策形成当前申报判断的次数。
- 未授权外发、上传或执行写操作的次数。
- 发布后阻断性安装失败率。

当前仓库尚未形成这些指标的统一基线。V1.2 应先定义事件和采集边界，再用两周试运行建立基线；在没有基线前不填写看似精确的增长目标。

## 10. 当前范围边界

### 产品内

- 政策检索与版本核验。
- 企业画像、财务、知识产权和行业定位的专业分析。
- 项目匹配、预评估、可行性、材料撰写和一致性检查。
- 知识库检索、证据台账、项目记忆和可控归档。
- 成员访问、Skills 分发、偏好同步和受控更新。

### 产品外

- 自动承诺企业符合或项目获批。
- 在无可靠来源时补造企业财务与经营数据。
- 自动提交政府申报系统。
- 未经授权发送客户材料或联系第三方。
- 替代律师、会计师或政府主管部门的正式意见。
- 通用 CRM、OA、项目排期和财务结算。

## 11. 需要主人确认的产品决定

1. 下一阶段是否正式采用“一个入口、一份项目档案、一条可验收闭环”作为 V1.2 唯一主线。
2. 核心用户是否继续限定为团队内政府项目申报工程师，知识产权顾问作为重要第二用户，而不是马上转向企业自助 SaaS。
3. 项目档案是否坚持本地优先，仅把经过授权的非敏感状态与团队知识库交互。
4. 后续版本是否继续暂停新增领域 Skill，除非真实任务证明现有 49 个能力无法覆盖。
