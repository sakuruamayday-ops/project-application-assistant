# 发布门禁瘦身与 Acceptance Harness 执行规则

状态：已实施

更新日期：2026 年 8 月 1 日

## 基线与目标

V1.4.5 整次发布的实际墙钟时间为 2 小时 22 分 46 秒。历史门禁报告中的
27.2 秒只代表部分可见子项，不得再作为整次发布耗时。

本次优化不删除安全核心，而是消除重复执行、历史安装流程和与 V1.4.5 无关的算法生成。
每次发布必须分别记录门禁运行、人工等待、发布操作与整体墙钟时间。

## 四层模型

| 层级 | 执行时机 | 核心责任 | 复用规则 |
|---|---|---|---|
| G1 代码与 Harness 收据 | PR 和候选发布 | 代码测试由 CI 执行；知识库验收验证已有收据 | 只有配置、索引、清单、构建器或 Harness 代码哈希改变时重跑 |
| G2 预发布运行时 | 服务候选状态 | REST 冒烟、`tools/list`、`knowledge_service_status` | 每次候选部署执行一次 |
| G3 发布产物 | 两个服务端下载入口 | ZIP 完整性、49 项 Skills、WorkBuddy 候选契约、旧组件排除 | 绑定产物 SHA-256，同包不重建 |
| G4 正式提升 | 主人明确批准后 | 验证签名索引与前三层证据，再提升 | 不重跑 G1，不改写发布者活动 Skills |

## Harness 收据

Harness 运行结果是可复用收据，必须绑定：

- 验收 profile 哈希；
- `manifest.jsonl` 哈希；
- `knowledge_content.sqlite3` 哈希；
- 索引构建器、隐私白名单构建器、Harness runner 和 engine 哈希。

任一输入变化时收据失效并闭锁阻断。输入未变时只验证收据，不再重跑整套
Harness。有依赖的检查必须声明 `depends_on`；前置失败时，后续项标记为 `blocked`，
不重复报出派生错误。

## V1.4.5 明确移出默认门禁的流程

- 项目算法包生成与校验，保留为后续独立项目；
- 双平台三步安装；
- 设备 ID、设备名称和设备请求头；
- 下载包内动态执行旧偏好迁移与三方合并脚本；
- 在正式提升中覆盖发布者真实 `~/.codex/skills`。

真实客户旧版迁移仍是用户安装协议的验收内容，但改由候选包契约和隔离安装沙箱覆盖，
不在每次线上提升时重复执行历史脚本。
