# 企业全生命周期助手 V1.2 PRD Lite

版本主题：任务总入口与项目作业闭环

状态：建议稿，尚未进入开发

更新日期：2026年7月26日

## 1. 背景

V1.1 已提供 56 个专业 Skills、团队知识库、门户、REST API、MCP 和发布治理。产品能力面已经较完整，但用户仍需要自行理解任务阶段、Skills 关系和多个输出之间的衔接。

门户现已提供面向全体登录成员的 Skills 管理中心，可检索和核验技能内容、文件与协作关系。这降低了能力发现和版本查验成本，但用户仍需知道应该选哪个技能、何时切换阶段以及如何延续同一客户任务，因此不改变 V1.2 的主问题。

如果继续增加 Skills 或界面入口，产品会进一步强化“能力很多”的印象，却不能证明“一个真实客户任务更快、更准地完成”。V1.2 应把已有能力组织成可恢复、可追溯、可验收的项目作业闭环。

## 2. 问题陈述

政府项目申报工程师在接到企业需求后，通常从模糊问题开始。当前系统能分别完成检索、分析、写作和检查，但缺少一个贯穿全程的项目档案与统一任务契约，导致：

- 不知道第一步应该做什么，或误把写作当成起点。
- 同一企业信息在不同环节重复提供、重复核验。
- 政策、企业、财务、知识产权和材料结论分散，难以快速复核。
- 中断后恢复成本高，下一次对话容易丢失已确认决定。
- 系统可用性主要由模块测试证明，缺少真实业务闭环验收。

## 3. 目标

让一名顾问只用业务语言提出任务，系统即可建立项目档案、选择正确工作流、复用已核验事实、展示证据与缺口，并将任务推进到可复核交付。

V1.2 的成功不是“增加了多少新功能”，而是以下三个结果同时成立：

1. 用户不需要知道 Skill 名称也能开始正确流程。
2. 同一客户事实和决定能够跨阶段复用。
3. 每次输出都能说明依据、缺口、质量状态和下一步。

## 4. 非目标

- 不新增大批领域 Skills。
- 不建设通用 CRM、OA 或完整项目管理系统。
- 不自动登录和提交政府申报。
- 不在本版本重构整个门户视觉系统。
- 不把全部客户原始材料默认上传团队云端。
- 不以自动生成完整申报书作为首要目标。

## 5. 核心用户场景

### 场景一：从模糊需求开始

用户说：“帮我看看这家公司今年能报什么项目。”

系统识别企业、地区、年度和资料状态，只追问会改变路线的关键信息，随后建立项目档案并进入项目匹配，而不是直接列政策或写材料。

### 场景二：目标项目已明确

用户说：“评估这家公司申报 2027 年小巨人的把握。”

系统直接进入对应预评估或材料体检路径，读取已确认的企业事实，列出政策基线、计算、三档判断、资料缺口和行动顺序。

### 场景三：继续上次任务

用户说：“继续上次这家企业的申报材料。”

系统恢复项目档案，先展示对象、目标、已确认决定、已用政策版本、未完成项和资料时效，再从中断环节继续。

### 场景四：交付前复核

用户说：“这版可以交了吗？”

系统执行适用的质量门禁，输出阻断项、建议修复项、证据覆盖和残余风险，不以“文字看起来完整”代替交付判断。

## 6. 方案概述

V1.2 新增一个贯穿 Agent Skills 的“项目作业包”。项目作业包不是新的客户数据库，而是本地优先的结构化任务档案，用于连接路由、证据、判断、交付和复盘。

### 项目作业包最小字段

| 字段 | 说明 |
|---|---|
| `case_id` | 本地唯一标识，不使用企业名称直接作为技术主键 |
| `enterprise` | 企业名称、统一社会信用代码或待确认状态 |
| `region` | 国家、省、市、区县及适用层级 |
| `target_year` | 申报或评估年度 |
| `target_project` | 标准项目名称或待匹配状态 |
| `stage` | 澄清、检索、匹配、评估、写作、检查、交付或归档 |
| `confirmed_facts` | 已确认企业、财务、知识产权和产品事实及来源 |
| `policy_baseline` | 管理办法、当期通知、核验日期和有效性状态 |
| `decisions` | 已确认判断、采用口径和理由 |
| `gaps` | 缺失资料、未核验事实和阻断项 |
| `deliverables` | 已形成文件或结构化输出的本地路径与版本 |
| `quality_status` | 未检查、阻断、有限通过或通过 |
| `next_action` | 下一步动作、责任方和触发条件 |

### 用户可见的统一任务摘要

每次重要阶段结束后，系统固定显示：

1. 当前结论。
2. 使用的现实依据与核验时间。
3. 仍缺什么。
4. 哪些内容已写入项目作业包。
5. 下一步建议。

## 7. 功能需求

### FR-1 统一入口与最小澄清

- `project-application-assistant` 继续作为唯一推荐入口。
- 系统根据业务语言识别对象、地区、年度、目标项目和任务阶段。
- 只追问会改变工作流或核心结论的缺口；普通任务默认不超过三个问题。
- 目标和资料已明确时不得重复询问。

验收标准：给定十条真实模糊需求，系统能为至少九条选择正确主流程，并把无法判断的一条明确标为需确认，不散弹调用多个领域技能。

### FR-2 项目作业包创建与恢复

- 新任务在完成最小识别后创建项目作业包。
- 同一企业可以有多个年度或多个目标项目，彼此不覆盖。
- 恢复任务时先展示上次状态与时效，再继续执行。
- 企业、目标项目或世界模式冲突时停止合并并提示用户确认。

验收标准：中断一个已完成政策核验的任务并在新会话恢复，不重复检索已核验且仍在有效期内的同一来源，能够准确显示待办和原决定。

### FR-3 证据与判断绑定

- 数字、日期、政策、企业事实和知识产权结论必须关联来源或计算过程。
- 事实、计算、推断、框架判断和待核验项可区分。
- 当前检索层未命中时只报告未命中，不推断不存在。
- 政策有效性变化时，将受影响判断标记为需复核。

验收标准：任取一条高风险结论，用户可以从任务摘要定位到来源、核验日期和使用它的判断。

### FR-4 阶段路由与交接

- 工作流至少覆盖澄清、检索、匹配、评估、写作、检查、交付和归档。
- 每个阶段声明输入条件、调用技能、输出契约和失败降级。
- 阶段完成后更新作业包，不依赖自由文本猜测上一步结果。
- 写作阶段不得跳过适用的政策与事实核验。

验收标准：三个金标准场景能从入口推进到质量检查，阶段状态和输出均可追踪。

### FR-5 质量状态与交付门禁

- 质量状态统一为未检查、阻断、有限通过和通过。
- 阻断项与建议项分开显示。
- 正式申报材料继续执行括号、数据、事实、关联和路径五步闸门。
- 未经用户授权不得自动外发、云端上传或提交。

验收标准：包含过期政策、财务勾稽错误和产品口径冲突的样例均被阻断；只有文字风格建议的样例不得误判为阻断。

### FR-6 端到端业务验收

V1.2 至少建立三条脱敏金标准任务：

1. 企业项目初筛与优先级路线。
2. 专精特新或小巨人申报前评估。
3. 正式材料交付前一致性检查。

每条任务包含输入、预期阶段、必须引用的证据类型、允许缺口、阻断条件和最终交付形态。

验收标准：发布门禁能自动或半自动输出每条任务的阶段完整率、证据覆盖率和阻断判断，不只报告单元测试通过。

### FR-7 产品事件与隐私边界

- 仅记录产品改进所需的最小事件，例如任务启动、首次有效判断、阶段完成、质量门禁和任务恢复。
- 默认不把客户名称、材料正文、财务数字、专利全文或凭据写入分析事件。
- 团队云端与本地作业包的字段边界必须显式配置并可审计。

验收标准：事件样例经过敏感字段扫描，不包含可识别客户材料；用户可知道记录了什么并能关闭非必要统计。

### FR-8 文档与版本单一事实源

- 产品名称、版本、Skill 数量和下载说明从套件清单生成或校验。
- 根 README、用户手册、发布页和门户不得出现互相冲突的当前版本。
- 历史 36 项、53 项和 2.x 口径只能作为明确标注的历史记录存在。

验收标准：发布门禁发现当前版本、Skill 数量或产品名称冲突时失败，并列出冲突文件。

## 8. 约束与依赖

- 现有 56 个 Skills 的输入输出并未全部结构化，V1.2 需要先定义最小公共契约，再逐步接入。
- 门户主应用文件体量较大，涉及门户状态展示的改动需小步进行并具备回归测试。
- 项目作业包必须兼容 Codex、WorkBuddy 和其他支持 Skills 的宿主，不能依赖单一平台私有记忆。
- 政策时效、企业数据和客户财务仍必须按既有真实性规则处理。
- 本地与团队云端之间的数据边界需在实现计划前完成威胁建模。

## 9. 成功指标

V1.2 先建立两周基线，再确认数值目标。发布评审至少观察：

- 首次有效判断时间是否下降。
- 三条金标准任务的闭环完成率。
- 关键结论证据完整率。
- 同一任务恢复后的重复提问和重复检索次数。
- 因政策版本、数据口径和跨章节冲突导致的返工次数。
- 阻断性安装或连接失败率。

## 10. 风险

### 最大产品风险

把项目作业包做成重型项目管理系统，反而增加顾问录入负担。应坚持自动提取、最小字段和业务输出驱动，不要求用户维护看板。

### 最大技术风险

不同 Skills 输出结构差异过大，导致作业包只能保存自由文本。应先覆盖三个金标准闭环，不追求一次接入全部 56 个 Skills。

### 最大信任风险

为了显示“已完成闭环”而隐藏资料缺口或把辅助来源当作正式政策。质量状态必须允许“有限通过”和“当前检索层未命中”。

## 11. 决定现在与验证下一步

### 现在需要决定

- 是否确认 V1.2 只围绕任务总入口与项目作业闭环推进。
- 是否同意暂停非阻断性的新增 Skill 和门户视觉重做。
- 是否确认项目作业包本地优先、云端最小化原则。

### 下一步验证

- 用三条真实脱敏任务验证最小字段是否足够。
- 统计现有 Skills 中首批需要结构化接入的 8 至 12 个核心能力。
- 建立两周产品事件基线后再确定正式目标值。

## 12. 进入实施前的产物

主人确认本 PRD 后，再创建一个 V1.2 feature 目录，并按 Spec Kit 的顺序形成：

1. `spec.md`：将 FR-1 至 FR-8 改写为可测试规格。
2. `plan.md`：明确作业包存储、跨宿主适配、隐私边界和迁移方案。
3. `tasks.md`：按基础契约、三条金标准、Skills 接入、门户展示和发布门禁拆分任务。
4. 完成评审后再进入实现，不把 PRD 直接当代码任务清单。
